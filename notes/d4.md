# Day 4 - SQLite Persistence

## Progress

Day 4 moved the chatbot from temporary browser state to persistent local chat history.

Instead of messages existing only inside the current webpage, the project now has the foundation for this flow:

**Browser page -> FastAPI `/chat` -> SQLite save -> Ollama -> SQLite save -> FastAPI response -> Browser page**

When the page opens, it can also rebuild the previous conversation:

**Browser page -> FastAPI history route -> SQLite messages -> Browser message list**

This is better because the conversation can survive page refreshes, browser closes, and backend restarts.

## What I Learned

### SQLite

- SQLite stores data in a local file instead of requiring a separate database server.
- Python includes `sqlite3`, so no extra database package is needed.
- Opening a connection to `data/companion.db` creates the database file if it does not exist.
- SQLite is local backend storage in this project, not browser-side storage.

### Tables and Rows

- A table defines the shape of a kind of data.
- A row is one saved record inside a table.
- The `conversations` table stores chat sessions.
- The `messages` table stores individual user and assistant messages.

### Primary Keys

- A primary key uniquely identifies one row.
- `INTEGER PRIMARY KEY` lets SQLite generate a numeric ID for each new row.
- Message IDs can also be used for chronological ordering in this simple app.

### Foreign Keys

- `messages.conversation_id` connects each message to a row in `conversations`.
- This creates a one-to-many relationship: one conversation can have many messages.
- `PRAGMA foreign_keys = ON` tells SQLite to enforce foreign-key rules.
- `ON DELETE CASCADE` means deleting a conversation would also delete its messages.

### Inserts and Selects

- `INSERT` adds a new row to a table.
- `SELECT` reads rows from a table.
- `WHERE conversation_id = ?` filters messages to one conversation.
- `ORDER BY id ASC` loads messages in the original chat order.
- SQL placeholders like `?` keep punctuation, quotes, and user text from breaking SQL statements.

### Python Database Access

- `sqlite3.connect()` opens a database connection.
- `connection.execute()` runs SQL.
- `with get_connection() as connection` manages the transaction.
- If the block succeeds, changes are committed.
- If the block fails, changes are rolled back.
- `connection.row_factory = sqlite3.Row` allows named row access such as `row["content"]`.

### Frontend Restoration

- The frontend can request saved history with `fetch()`.
- `loadHistory()` clears the current message list and rebuilds it from saved messages.
- History should load once when the page opens.
- New messages should continue to be added normally during the active session to avoid duplicates.

### History Versus Memory

- Saved chat history stores what was said.
- Long-term memory would extract reusable facts, preferences, or summaries.
- Day 4 adds persistence, but not emotional memory or long-term memory yet.

## Key Terms
