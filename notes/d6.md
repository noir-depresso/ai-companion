# Day 6 - Backend Reliability and Chat Controls

## Progress

Day 6 moved the chatbot from a basic working demo toward a more reliable application that is easier to test and control.

Instead of the browser and backend each owning separate assumptions, the project now follows this flow:

**Browser settings -> FastAPI settings route -> validated chat request -> Ollama options -> timed response -> Browser display**

The user can also clear the current conversation without manually editing the SQLite database.

This is better because generation settings have one source of truth, backend failures produce useful responses, and common testing actions can be performed from the browser.

## What I Built

- Added a `/settings` route that exposes the model and generation settings to the frontend.
- Connected the temperature control from the browser to the FastAPI request and Ollama options.
- Added routes for deleting the default conversation's saved messages.
- Added a Clear History control to the browser interface.
- Added response-time measurement around the Ollama generation call.
- Displayed the response time after successful assistant replies.
- Added specific handling for Ollama response and connection failures.
- Kept unexpected failures logged by the backend.
- Centralized model and sampler defaults in `app/config.py`.
- Changed message saving so a completed user/assistant exchange could be stored together after generation succeeded.

## What I Learned

### One Source of Truth

- Generation defaults should live in the backend instead of being duplicated in Python and JavaScript.
- A settings route lets the browser discover the current minimum, maximum, step, and default temperature.
- A frontend control only works when its value reaches the request model and is passed into Ollama.
- Centralized constants make later model or sampler changes easier to reason about.

### Error Handling

- Ollama can reject a request even when the FastAPI server is running.
- A failed connection is different from a model response error.
- FastAPI can translate backend failures into useful HTTP status codes.
- `502` is useful when Ollama returns an error, while `503` is useful when Ollama cannot be reached.
- Unexpected exceptions should be logged so the original problem is not hidden.

### Atomic Message Saving

- Saving the user message before generation can leave an incomplete exchange if Ollama fails.
- Saving both messages in one database transaction keeps successful exchanges together.
- A transaction commits when its block succeeds and rolls back when an exception interrupts it.
- Database behavior should match what the user sees in the browser.

### Browser Controls

- A Clear History button calls a backend `DELETE` route instead of directly changing SQLite.
- Clearing the visible message list is not enough; the saved rows must also be deleted.
- Browser controls should disable or reset themselves at appropriate times.
- Cached JavaScript can make a correct backend change appear broken, so a hard refresh may be needed during testing.

### Measuring Responses

- `time.perf_counter()` can measure how long the Ollama generation call takes.
- The elapsed time should describe model generation, not unrelated page-loading work.
- Response metadata can be returned through the same Pydantic response model as the assistant message.

## Key Terms

Source of truth, generation settings, temperature, sampler, HTTP status code, `ResponseError`, `ConnectionError`, transaction, atomic operation, rollback, `DELETE` route, response time, `perf_counter`, backend logging.

## Day 6 Result

By the end of Day 6, the chatbot had backend-owned generation settings, working browser controls, clearer failure handling, and response-time feedback.

The application was more reliable to test, but Rin's personality was still based on one fixed prompt. The next step was to create a persistent internal companion state.
