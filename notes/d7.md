# Day 7 - Persistent Companion State

## Progress

Day 7 moved Rin from having only a fixed character prompt toward having a persistent internal state.

Instead of every conversation starting from the same relationship and emotional conditions, the project now has this foundation:

**SQLite companion state -> Python `CompanionState` -> developer routes -> updated SQLite state**

This is better because trust, closeness, respect, comfort, mood, energy, and stress can exist independently from the chat transcript and survive backend restarts.

## What I Built

- Created a `CompanionState` dataclass for Rin's internal values.
- Added default values for trust, closeness, respect, comfort, mood, energy, and stress.
- Added a `clamp()` function that keeps numerical values between 0 and 100.
- Added mood validation and a small set of allowed moods.
- Created the `companion_state` SQLite table.
- Restricted the table to one state row with `id = 1` for the current single-companion design.
- Inserted the default state when no saved state exists.
- Added database functions for loading and saving companion state.
- Added Pydantic models for state data sent through the API.
- Added developer routes for viewing, changing, and resetting state.
- Added a developer panel for inspecting state and previewing the current prompt.

## What I Learned

### Internal State

- Chat history records what was said, while companion state records Rin's current relationship and emotional conditions.
- Relationship values such as trust and closeness should persist across messages.
- Temporary values such as mood, energy, and stress can influence the current tone without rewriting Rin's identity.
- Keeping state separate from the transcript makes it easier to inspect, validate, and update.

### Dataclasses and Pydantic Models

- A dataclass is useful for internal Python state and automatically provides common object behavior.
- A Pydantic model is useful at the API boundary because it validates incoming and outgoing data.
- Internal state and API models can represent similar information while serving different responsibilities.
- Conversion functions keep the database/domain object separate from the web response model.

### State Validation

- `clamp()` prevents numerical state from going below 0 or above 100.
- Allowed mood values prevent spelling mistakes or unknown moods from entering the system.
- Validation should occur before state is written to SQLite.
- Database `CHECK` constraints provide another layer of protection.

### A Single State Row

- `CHECK (id = 1)` limits the current table to Rin's one global state row.
- `INSERT OR IGNORE` adds defaults the first time without overwriting an existing state.
- The single-row design is suitable while the app has one companion and one user.
- A future multi-user or multi-companion version would need state rows connected to their owners.

### Developer Tools

- A `GET` route can expose the current state for inspection.
- A `PUT` route can validate and save edited state values.
- A reset route can restore all default values.
- A prompt-preview route makes hidden system instructions visible during development without exposing them in normal chat replies.

### Schema Changes

- `CREATE TABLE IF NOT EXISTS` creates a missing table but does not modify an older table definition.
- Existing SQLite data may require a migration when the schema changes.
- Development databases can sometimes be recreated, but important data should be backed up before migration.

## Key Terms

State, dataclass, domain object, Pydantic model, validation, clamp, constraint, `CHECK`, `INSERT OR IGNORE`, single-row table, persistent state, developer route, schema migration.

## Day 7 Result

By the end of Day 7, Rin had a persistent, validated internal state that could be viewed, edited, reset, and stored independently from conversation history.

The values existed, but numbers alone could not guide the language model. The next step was to interpret them as concise behavioral instructions in Rin's system prompt.
