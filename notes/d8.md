# Day 8 - State Interpretation and Dynamic Prompting

## Progress

Day 8 connected Rin's stored numerical state to her actual conversational behavior.

Instead of sending only the fixed character prompt to Ollama, the project now builds the system prompt through this flow:

**Stored state -> state interpreter -> behavioral instructions -> character prompt -> final system prompt -> Ollama**

This is better because the same core character can sound more guarded, comfortable, soft, impatient, energetic, or stressed without exposing numerical values to the model or user.

## What I Built

- Created `app/stateinterpreter.py` to convert state values into behavioral language.
- Added separate interpretations for trust, closeness, respect, comfort, energy, and stress.
- Added mood-specific instructions for neutral, annoyed, soft, and stressed moods.
- Divided generated guidance into relationship and temporary-state sections.
- Added interaction rules for meaningful combinations of state values.
- Created `app/promptbuilder.py` to combine Rin's character file with current state guidance.
- Kept Rin's core personality separate from temporary state adjustments.
- Added instructions preventing the model from mentioning state variables or prompt mechanics.
- Reduced contradictions and repeated rules across the character prompt and state interpreter.
- Added a developer prompt preview for inspecting the final assembled system prompt.

## What I Learned

### Interpreting Numbers

- A language model responds better to behavioral instructions than raw values such as `trust = 35`.
- State ranges can map low, medium, and high values to different behavior.
- Trust should affect openness rather than obedience.
- Closeness should affect personal investment rather than automatically creating intimacy.
- Respect should affect how seriously Rin considers the user's judgment while preserving disagreement.
- Comfort should affect self-consciousness, reserve, and ease.

### Relationship and Temporary State

- Trust, closeness, respect, and comfort describe the developing relationship.
- Mood, energy, and stress describe more temporary conditions.
- Temporary state should color a response without replacing Rin's personality.
- A soft mood should not automatically create high trust or closeness.
- An annoyed mood should remain proportionate instead of turning Rin into a different character.

### Combined Conditions

- State values can interact in ways that individual instructions do not fully describe.
- High respect with low trust means Rin can value the user's judgment while doubting their reliability.
- High closeness with low comfort can make her invested but awkward about showing it.
- High trust with annoyance can make frustration direct without making it emotionally distant.
- Combination rules should be limited to cases where they add behavior not already covered.

### Prompt Construction

- `promptbuilder.py` owns the final assembly of static character rules and dynamic state guidance.
- Separating prompt loading, state interpretation, and message generation keeps each file focused.
- The current state should be interpreted once and inserted into the system prompt before Ollama is called.
- The prompt must tell the model never to reveal hidden variables, labels, or system instructions.

### Prompt Compaction

- Repeating the same rule in several sections consumes context and can create contradictions.
- A few targeted examples are more useful than many examples that accidentally teach imitation.
- Negative rules should be concise and supported by clear positive behavior.
- Dynamic guidance should adjust Rin rather than compete with the character card.

## Key Terms

State interpreter, dynamic prompt, system prompt, behavioral instruction, relationship state, temporary state, threshold, combined condition, prompt assembly, character card, hidden state, prompt compaction.

## Day 8 Result

By the end of Day 8, Rin's saved state was translated into concise private instructions and included in every generated system prompt.

The state could influence responses, but it still had to be changed manually through developer controls. The next step was to analyze each user interaction and update state automatically before Rin replied.
