# Day 9 - Interaction Analysis and Automatic State Changes

## Progress

Day 9 moved Rin from manually controlled state toward automatic relationship and mood changes based on user interactions.

Each new message now follows this intended flow:

**User message -> recent context -> interaction analysis -> requested changes -> limited state changes -> saved new state -> updated system prompt -> Rin's response**

The interaction and its requested changes are also stored so the system can be inspected later.

This is better because Rin responds from the state created by the user's latest message instead of replying from the old state and updating afterward.

## What I Built

- Created an `InteractionAnalysis` Pydantic model for structured analysis results.
- Defined supported event types such as compliments, affection, apologies, insults, disagreements, boundary events, supportive actions, and jokes.
- Added requested deltas for trust, closeness, respect, and comfort.
- Added interaction importance, suggested mood, and a short reason.
- Created `app/interactionanalyzer.py` to ask Ollama for a validated structured analysis.
- Added conservative analysis rules so ordinary conversation usually causes little or no change.
- Created `app/statechange.py` to limit and apply requested relationship changes.
- Scaled the maximum allowed change according to interaction importance.
- Restricted mood changes according to the analyzed event type.
- Added recent-message loading with newest-first selection and chronological output.
- Created an `interaction_events` SQLite table for saved state-change requests.
- Saved each user message before linking its analysis event through `message_id`.
- Reordered the chat route so the updated state is saved and passed into `llm.py` before Rin's response is generated.

## What I Learned

### Structured Interaction Analysis

- The analyzer should request changes but should not directly mutate state.
- A Pydantic schema constrains Ollama's output to known event types and valid ranges.
- Structured output is easier to validate and apply than parsing free-form text.
- The latest user message should be analyzed with enough recent context to understand its meaning.
- Conservative rules reduce exaggerated reactions to ordinary conversation.

### Requesting Versus Applying Changes

- The analyzer can request a delta between -5 and 5.
- The state-change layer decides how much of that request is actually allowed.
- Separating these steps prevents the model from having unrestricted control over persistent state.
- Low-importance events can produce no relationship change.
- Larger changes are reserved for more important interactions.

### Mood Safety

- Not every event type should be allowed to produce every mood.
- A compliment may reasonably suggest neutral or soft, but should not directly create a stressed mood.
- An insult may produce annoyed or stressed without changing Rin's core personality.
- If a suggested mood is not allowed for the event, the current mood is preserved.

### Recent Context Queries

- An exchange normally contains one user message and one assistant message, so the exchange limit is multiplied by two.
- `ORDER BY id DESC LIMIT ?` selects the newest messages efficiently.
- The selected rows must then be reordered with `ORDER BY id ASC` before they are shown to the analyzer.
- This preserves chronological reading order while still selecting the latest part of the conversation.

### Event Storage

- `interaction_events` records what the analyzer requested and why.
- `conversation_id` links an event to its conversation.
- `message_id` links the event to the exact user message that caused it.
- Foreign keys prevent events from pointing to messages or conversations that do not exist.
- Storing analysis separately from current state creates an audit trail for later debugging and tuning.

### Execution Order

- The user message must be analyzed before the assistant prompt is built.
- `main.py` coordinates the processing order.
- `interactionanalyzer.py` requests changes.
- `statechange.py` limits and applies changes.
- `database.py` stores messages, state, and interaction events.
- `promptbuilder.py` interprets the updated state.
- `llm.py` builds messages and calls Ollama using that updated state.
